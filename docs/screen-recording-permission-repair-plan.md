# LiveSub 屏幕与系统音频权限修复建议

日期：2026-09-28；2026-09-29 更新。状态：本机正式包权限恢复、短时真实系统音频字幕、停止／重试及更新后授权连续性已验收；其他 Mac 分发和长期稳定性未验证。

实施记录：正式包构建要求明确提供有效代码签名身份，三个预览模式使用独立标识与显示名称；原有六份旧／预览 `.app` 已移入废纸篓并注销旧应用注册，`dist/` 只剩正式包。为本机创建的自签证书仅供本机代码签名，未完成公证或分发验收。ScreenCaptureKit 错误按系统域和错误码分类，预检查为 false 时调用合法的授权请求入口，保留失败阶段及请求结果诊断。经用户授权仅重置 `local.jujube.livesub` 的 ScreenCapture 记录；TCC 对当前正式包及一次代码变化后的新包均报告 `Allowed` 且指定要求匹配。`./script/test.sh` 通过；安静环境中播放 4.204 秒公开样本，两次系统音频字幕均包含已知参考语句主体，停止／重试通过。以下只读诊断快照保留为历史记录，当前结果见 [实机测试矩阵](manual-test-matrix.md)。

目标是让授权能够稳定对应实际运行的 LiveSub，并在失败时给出可核实的原因。验收必须包括真实系统音频采集；编译通过、签名校验通过、权限开关开启，都不能单独代表问题已经解决。

**诊断依据与结论边界**

| 当前运行包 | `dist/LiveSub.app`，进程 85190，于 20:07:57 启动 | 此进程启动晚于上述失败；本次未重新触发采集 |

因此，可以确认故障层级是系统权限校验；“临时签名变化与同标识副本使既有授权无法匹配”是目前最有证据的根因假设，但尚未被直接证明。上述时间、进程号和哈希属于诊断快照，实施时应重新核对。

Apple 说明，macOS 使用代码的 Designated Requirement（DR，指定要求）判断更新前后是否是同一应用；临时签名的 DR 绑定具体代码版本，无法可靠地跨版本追踪授权。[Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)

**建议按以下顺序实施**

1. **先固定正式应用的身份，再处理权限记录。**

   保留正式包的 `local.jujube.livesub` 标识与固定启动路径，修改 `script/build_and_run.sh` 的签名步骤：从明确指定的签名身份读取配置，不再让需要稳定权限的正式构建默认使用 `--sign -`。优先复用适合当前分发方式的现有证书；本地开发可采用稳定的 Apple Development 身份，对外分发另行评估 Developer ID 与公证。

   缺少指定身份时应清楚报错，不能静默退回临时签名。此次尚未检查钥匙串是否存在合适证书；若需要创建、导入证书或调整钥匙串设置，应先确认具体方案。现阶段不需要购买账号、安装完整 Xcode 或增加项目依赖作为先决条件。

   验证重点是连续两个不同构建是否保持兼容的 DR，不能只比较应用名称、Bundle ID 或签名命令是否成功。不要通过把安全身份要求简化为仅检查 Bundle ID 来绕过问题。

2. **隔离正式包与各预览包的标识。**

   建议正式包保持原标识，预览包分别使用独立标识，例如 `local.jujube.livesub.preview.icon`、`local.jujube.livesub.preview.ui`、`local.jujube.livesub.preview.qwen`。同时设置可区分的显示名称，如“LiveSub UI Preview”，避免权限列表里多个条目都叫 LiveSub。

   构建脚本应根据构建模式统一生成应用路径、显示名称、Bundle ID 和签名配置；完成 Info.plist 与资源打包后再签名。纯界面预览若继续使用临时签名，应明确其用途，不能把其权限表现作为正式包验收结果。

   实施前盘点现有四份副本及其使用情况。需要继续使用的预览版按独立标识重新打包；历史同标识包的归档或移除另行确认，不自动删除，也不在签名后直接修改 Info.plist。预览版改变 Bundle ID 后会使用新的偏好设置域，旧设置应保留，是否迁移另行决定。

3. **改进失败分类与最小诊断信息。**

   当前 `SystemAudioCapture.captureError` 在发生错误后，只要 `CGPreflightScreenCaptureAccess()` 返回 false，就统一给出授权提示。建议首先依据 ScreenCaptureKit 的错误域和错误码分类，明确区分授权拒绝、缺少 entitlement、采集服务启动失败及其他运行错误；预检查结果作为辅助信息保留。

   对 `SCStreamError.userDeclined`，可以提示：“macOS 未允许当前版本的 LiveSub 访问屏幕与系统音频；若设置中已开启，请核对当前应用版本与授权状态。”不能仅凭预检查结果断言用户没有打开开关，也不能自动断言签名已失配。[Apple 对 userDeclined 的定义](https://developer.apple.com/documentation/screencapturekit/scstreamerror/userdeclined)

   保留失败阶段（`discover displays` 或 `start stream`）、错误域、错误码、预检查结果、应用标识、版本和当前应用路径。底层描述在必要脱敏后用于诊断；不记录音频、字幕内容、窗口标题或后端认证令牌。签名详情优先通过只读诊断命令核对，无需为了报错处理引入复杂签名管理模块。

   初次没有权限时仍须保留合法的系统授权入口；不能添加一个仅因预检查为 false 就永久阻止授权请求的前置拦截。

4. **身份稳定后，再做一次针对目标应用的授权恢复。**

   先核对准备运行的确切应用路径、Bundle ID 和签名，确认正式包未被旧构建覆盖。经授权完全退出对应应用，针对该应用重新确认权限，再启动同一份包。Apple 的 ScreenCaptureKit 示例也要求授权后重启应用以启用采集。[Apple ScreenCaptureKit 示例](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos)

   如果正常重新授权仍然失败，且证据指向旧授权记录，再评估仅重置 `local.jujube.livesub` 的 ScreenCapture 授权。重置会撤销该标识对应的既有授权，必须先说明影响并获得明确授权；不作为构建脚本或应用启动时的自动行为。

   不做全局 TCC 重置，不直接写权限数据库，不关闭系统安全保护，也不把重启系统权限服务作为默认修复步骤。

5. **最后进行真实采集与更新后复测。**

   在获得启动应用与采集测试的授权后，用一段用户指定、非受保护且内容已知的本地音频做短时系统音频测试。明确选择系统音频来源，确认收到连续音频帧、已知语句进入原文字幕，并检查停止后资源释放。

   然后用相同签名身份构建一个代码确实有变化的新版本，退出并替换旧包，再测试原有授权是否仍然有效。还应验证新标识的预览版不会冒用正式包的授权。复测可验证稳定性及问题是否仍然复现；由于缺少历史授权记录，即使复测成功，也不能倒推已经证明旧记录的具体失配原因。

   如果身份隔离与重新授权后仍出现 `TCC Disallow`，应保留该次请求时间和应用身份，继续排查授权生效状态、系统策略或 ScreenCaptureKit 行为；不能宣称签名调整已解决问题，也不能据此直接更换识别模型。

**预计修改范围**

| 文件 | 建议修改 |
|---|---|
| `script/build_and_run.sh` | 稳定签名配置、不同构建模式的应用标识与名称、明确失败提示 |
| `app/LiveSub/Audio/SystemAudioCapture.swift` | 按原始错误分类、保留阶段与诊断信息 |
| `app/LiveSub/Audio/AudioCaptureService.swift` | 必要的错误类型和用户提示调整 |
| `app/LiveSub/App/AppController.swift` | 正确展示权限类错误与一般采集错误；仅在需要时调整 |
| `app/LiveSubTests/AudioPipelineTests.swift` | 覆盖权限错误分类的回归风险，复用现有检查入口 |
| `docs/known-issues.md`、`docs/manual-test-matrix.md` | 根据真实复测结果更新状态；保留未验证项 |

建议拆成“签名与包身份”和“错误分类与诊断”两组可审查改动，再执行需要系统交互的授权恢复与验收。已有未提交修改需要保留，不能用本方案覆盖其他正在进行的工作。

**验证与完成标准**

本次仅新增建议文档，没有运行以下修复验证。未来实施后的验证分三层：

| 层级 | 内容 | 通过标准 |
|---|---|---|
| 静态与自动检查 | 对照 Info.plist、签名与构建模式；运行错误分类回归检查和现有 `./script/test.sh` | 正式与预览身份分离；不同错误不会被统一误报；相关检查通过 |
| 构建身份检查 | 检查两个不同构建的 DR，验证新版本满足原版本的身份要求 | 身份连续性成立；不只检查包自身签名完整性 |
| 原生运行验收 | 授权后启动、短时系统音频、停止与重试、重建更新后复测 | 实际获得音频并产生匹配已知内容的字幕；停止后释放采集；更新后既有授权可用 |

错误分类的回归检查至少应包含：系统明确拒绝授权；非权限类启动失败且预检查为 false；预检查为 true 但流仍启动失败。测试不应真实申请权限或开始采集。

`./script/test.sh` 已有 Python、Swift 音频、字幕、悬浮窗、后端协议与构建检查，其中后端传输检查会运行有明确结束条件的本地回环测试。它不能代替原生屏幕录制权限验收。本次不启动开发服务、不重新构建或替换应用、不安装依赖。

完成报告应分别说明：配置与代码是否修改、自动检查是否通过、授权是否恢复、真实系统音频是否可用，以及不同构建间是否保留授权。只有这些证据对应到同一目标应用，才能报告“修复完成”。
