# 仅译文显示与延迟改进

日期：2026-09-26。本轮已完成三组真实模型 IPC 前后对比、整套回归、最终构建及未录音状态的原生显示切换检查。最终译文等待在这些样本中降低，首条译文基本持平，不能推广为所有场景的延迟保证。上一轮术语与段落验证见 [历史记录](terminology-and-paragraphs.md)。

## 显示方式

主窗口工具栏的“字幕显示”和菜单栏菜单都可切换“双语／仅译文”。默认双语；选择保存在本机，重开 App 后继续使用。两处入口及主窗口、悬浮层共用同一偏好。

仅译文时，主窗口隐藏原文栏并让译文使用整个阅读区域；悬浮层隐藏原文、采用较矮面板。翻译尚未到达时保留“翻译中…”状态，失败时显示翻译失败。切换是显示操作，不重启会话、不删除原文、不重做识别；恢复双语后仍可阅读源文。复制与 TXT／Markdown 导出继续保留双语。

主窗口仅译文模式在源文修订后可暂留上一版已配对译文，并明确标注“上一版译文·更新中…”，减少阅读区反复变为空白的情况；这不是当前修订已翻译完成。双语模式和导出仍采用严格的当前修订投影，不把旧译文与新原文组成一对。

代码涉及 `SubtitleDisplayMode.swift`、`AppController.swift`、`TranscriptView.swift`、`LiveSubApp.swift` 与 Overlay 展示模块。偏好使用现有系统存储；未新增外部依赖或模型，Swift 内部增加了 `LiveSubOverlay → LiveSubSubtitles` 的 target 依赖关系。

## 延迟改动范围

本轮后端实现两项局部调整，并通过回归与真实 WAV IPC 对比检查效果：

- 保留 750 ms 的预览节流间隔，但在间隔内保存最新修订，并在到期时提交尚未处理的最新预览，避免最新源文只因没有后续 ASR 事件而一直等到 final。
- 以相同 session／generation／segment、原文和渲染后 prompt 为缓存键，有界复用模型原始输出；revision 可以变化，因此内容未变的预览到 final 可以省去重复推理。每次请求仍重载词库并使用当前目标词恢复保护标记；仅目标译法改变而 prompt 相同也能立即生效，无须保证重跑模型。缓存键变化则重新推理，结果仍使用当前请求身份。

此次不更换 ASR／翻译模型，不调整 ASR 分段，不增加说话人功能或外部依赖。“仅译文”只减少屏幕内容，本身不减少模型推理量。

## 测量方法与改前基线

以相同 WAV 按实时节奏输入本机后端，客户端记录 WebSocket IPC 收到的字幕事件。模型与音频哈希保存在原始报告；改前代码哈希见 [源文件清单](latency-source-before.json)。这套指标排除原生音频采集及 Swift 窗口渲染，不是“说完一句话到屏幕显示”的延迟。

“首条可用译文”是非空 preview／final 且带有非空已翻译源文；“有效预览”额外要求与当前源文和修订匹配。“最终原文到最终译文”等待从客户端首次观察到对应 final 原文修订开始，不是后端内部 ASR 完成时刻。以下中位数按每段等待计算，样本很小，仅作为本次前后比较基线。

| 样本 | 时长 | 音频开始到首条可用译文 | final 原文到 final 译文等待中位数／最大值 | 有效预览事件 | 最终段数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| [公开英文人声](latency-before-en.json) | 11.000 s | 1111.93 ms | 663.62／854.84 ms | 5 | 4 |
| [公开中文人声](latency-before-zh.json) | 6.740 s | 1606.03 ms | 871.25／950.02 ms | 1 | 2 |
| [Daniel 技术语句合成音频](latency-before-technical-tts.json) | 10.010 s | 605.76 ms | 739.24／1073.25 ms | 1 | 5 |

三份基线报告均 `passed=true`，最终源译修订配对正确，无报告错误、重复 final 或 final 状态倒退。技术样本是本机 TTS 合成语音，不是真实讲座；本轮这份 TTS 基线经过完整 IPC，与上一轮直接调用 ASR → translator 的 `terminology-audio-tts.json` 测量路径不同，不应混用数字。

## 改后同样本结果

逐份核对改前／改后音频 SHA256 相同；三份改后报告均 `passed=true`，最终段数仍为 4／2／5，无错误、重复 final 或源译修订错配。

| 样本与改后报告 | final 原文到 final 译文等待中位数，改前 → 改后 | 中位数变化 | 改后最大等待 |
| --- | ---: | ---: | ---: |
| [英文人声](latency-after-en.json) | 663.62 → 556.53 ms | 降低约 16.1% | 625.61 ms |
| [中文人声](latency-after-zh.json) | 871.25 → 493.88 ms | 降低约 43.3% | 544.33 ms |
| [技术 TTS](latency-after-technical-tts.json) | 739.24 → 572.30 ms | 降低约 22.6% | 661.67 ms |

每个样本改前、改后各运行一次，段数少，不能证明通用性能提升或长期 P95。上述结果是调度与复用组合改动的测量，不能分别归因于某一策略。

| 样本 | 音频开始到首条可用译文，改前 → 改后 | 有效预览事件，改前 → 改后 |
| --- | ---: | ---: |
| 英文人声 | 1111.93 → 1080.40 ms | 5 → 2 |
| 中文人声 | 1606.03 → 1576.23 ms | 1 → 1 |
| 技术 TTS | 605.76 → 638.06 ms | 1 → 2 |

首条译文基本持平；技术 TTS 反而慢 32.30 ms。有效预览数量也没有全部增加，因此不能声称所有预览指标均改善。这轮可支持的结论是：三组有限样本的最终译文等待降低，首译速度尚未观察到明显一致改善。

### 最终包与原生操作

`./script/build_and_run.sh --verify` 通过 release 构建、bundle、Info.plist 与 strict ad hoc codesign 检查。包位于 `dist/LiveSub.app`，`Contents/MacOS/LiveSub` 的 SHA256 为 `7926d5d8202fc3383cb1793d403ecd5544ed0d2aeb70bc2cb27a05edd56f7378`。打包后的四个已核对 Python 运行文件与源码逐字节一致。

实际 CUA 操作确认：在新包主窗口 idle、0 段字幕状态点击“仅译文”，可访问性树中的原文栏消失，译文语言与空态更新；Cmd+Q 后无 App／后端残留。重新打开仍选中“仅译文”，切回“双语”后原文栏恢复。开启悬浮层、切到仅译文、隐藏悬浮层期间状态始终 idle，未启动录音；最后退出无残留，最终保存偏好为 `translationOnly`。

本轮未实际点击菜单栏的额外显示入口；说话过程中切换的会话保持仅由合成 controller 断言覆盖，未以现场采集验证。CUA 截图只返回倾斜缩略图，不能用作运行窗口的像素确认；视觉结论限于已检视的生产视图合成图。真实音频到屏幕的全链路延迟仍未知。

上一轮包哈希与测试结果保持历史快照，不作为本轮完成证据。系统音频 ScreenCaptureKit `-3801`、原生采集准确率以及全部历史人工验收未由本轮工作解决。
